# Exit from the hidden-bubble notification

User request: add Exit next to Open chats in the hidden-bubble notification; stop Buddy until explicitly reopened. User selected both a logical Exit and an OS Force stop route after the Android limitation was explained.

Notification actions: Open chats (unchanged), Exit (Buddy shutdown), Force stop… (immutable activity PendingIntent to a nonexported exit activity, which latches Exit before opening this package's Android app-info screen; user presses Force stop). Android's privileged force-stop API is unavailable to ordinary apps. Logical Exit can leave a system-recreated idle accessibility/listener process, but must not restart Buddy work. Do not disable permissions, clear data, change safety controls or credentials, or automatically restart the private SSH tunnel.

Persist exited synchronously before shutting down. Last native process starts (Java builders and PTYs) share its lock, refusing starts after exit begins. Stop MCP/request effects, overlays and wake locks; cancel pending schedules and notifications without deleting saved plans; close Buddy's tasks. Let the background browser close and save through a bounded, captured-process teardown before ending app-owned native/Linux/terminal/tunnel processes. Keep the system-bound Java service quiescent instead of self-killing: actual tests showed Android marks self-killed accessibility services crashed and will not reliably rebind. Preserve queued chat files/order/preferences before completing Exit; failed saves keep in-memory data and explicit reopen retries them. Advancing work generations cancels obsolete producers/callbacks across reopening; native starts are atomic with Exit. Clear interrupted tasks' temporary approval grants, preserve scheduled grants, and refresh call-notification state on reopening. Explicit launch during shutdown is refused with an explanation until shutdown finishes. Only Main/Share user entry clears the persisted exit flag, never application/service/boot/notification creation. Already-bound idle accessibility services can start runtime on explicit reopen. Passive services/receivers and scheduled/rule pumps remain gated after Android restarts the process. Source guards must preserve app approval and cancellation boundaries.

Proof: build with release lint; focused lifecycle tests on emulator: notification actions and own-package Settings destination, Exit drops MCP/bubble/native children/tunnel while retaining the bound accessibility service, queued chat state survives, stale show/boot/notification events cannot resume, explicit Main/Share reopen resumes without new permission or credential setup. Verify Force stop through Android's own UI separately. Observed emulator behavior: Android may disable accessibility and rebind the notification listener even before explicit reopen; the shared persistent exit gate must keep such a process idle. Restore only preexisting emulator permissions after this check. Run repository helper/phone/version fixtures, diff-check, cleanup and full council before landing. Current request authorizes local implementation and verification only; no commit/push/release/physical-phone deployment is requested for this change.
